# 同房间再来一局：设计草案

日期：2026-10-20（America/Los_Angeles）。需求：REMATCH-001，[原需求存档](../../NEW_FEATURE_REQUIREMENTS_2026-10-20.md)及 [Issue #2](https://github.com/yup005/note_wolf/issues/2)。

状态：Owner 在审阅草案后回复“继续”（2026-10-20），按本方案进入[实施计划](../plans/2026-10-20-rematch.md)，尚未实施。此确认不把需求矩阵改成已实现。产品目标和验收来自原 Issue，不重新裁定玩法或增加部署授权。

## 目标与成功条件

房主在已结束且可靠归档的对局中发起“再来一局”。房间 ID、四位房间号、玩家会话和座位保持，新一局回到候场，重新准备和发牌。上一局的官方事实、个人草稿、发布版本、收藏、有效分享及其授权独立保留。

同一次动作重试、两个设备并发、响应丢失或服务重启均只能创建一局。归档失败时整个操作回滚，上一局保持可读，不能出现部分清空。新局的临时房主、法官和已知秘密不能继承上一局授权。

## 已核实的现状

- `packages/storage/lobby.ts` 建立房间、成员、准备、身份、夜晚、白天及历史表；实时状态以房间为主键，当前没有独立每局标识。
- `packages/storage/records.ts` 的 `record_rooms.room_id` 同时充当归档对局标识；草稿、版本、个人删除边界及手动修订依赖该值。`capture` 已有归档便直接返回，不能清空实时状态后继续以同一归档键记录第二局。
- `saved_replays` 以用户和旧对局 ID 唯一；收藏、个人命名、分享、评论、通知已经存在，需保持原 ID 和权限。
- `preserveForRoomCleanup` 已能保留官方文档与胜负事实，但不等于完整的重开归档门禁。自动回放目前仍需实时 day/night/history，必须在重开清理前冻结。
- `apps/server/app.ts` 既有 `/api/rooms/:id/record*` 路径把 ID 当作记录所属对局；若直接改成“当前局”，旧标签页可能误改新局。
- `useRoom.ts` 以房间 revision 接收快照；只依赖轮次、turnId 或组件仍然挂载，不能阻止同一房间前后两局之间的迟到私密响应。

## 方案比较与建议

| 方案 | 代价和效果 |
| --- | --- |
| 推荐：保留实时房间表，增加每局注册和归档关联 | 房间与成员不迁移；已有归档 ID 保留。记录层明确区分实时房间与固定对局，接口显式绑定 gameId。需要集中梳理记录、授权和实时请求的边界。 |
| 所有实时与历史表整体改为 game_id | 数据语义统一，但需要迁移大量运行表及外键，扩大本次风险；对一次只有一局的实时房间收益有限。 |
| 为下一局创建新房间并复制座位 | 实现入口较少，但房间 ID、订阅及返回路径改变，不满足同房间目标。 |

推荐第一种。现有实时表继续只表示房间当前一局；完成归档的历史读取不得回落到该房间的新实时状态。

## 数据模型与兼容

新增 `room_games`，保存不可变的 `id`、所属 `room_id`、局号和创建时间，约束同房间局号唯一。此表不随实时房间删除而级联删除，历史关联和归档授权需独立保留。

新增 `room_game_heads`，以实时 `room_id` 唯一关联当前 `game_id`；实时房间清理仅删除 head 和原运行表。`RoomSnapshot` 增加公开的 `gameId` 和 `gameNumber`，原 `id`、`code`、revision 继续表示房间。revision 跨局单调增加。

第一次迁移中，现存房间及独立归档的首局 `game_id` 使用原 ID；同一 ID 只建一条注册记录，迁移事务可重复运行。已有发布记录 ID、收藏 ID、分享 token、个人命名、评论和通知来源不重写。新房间第一局也可沿用房间 ID；后续局使用新 UUID。

归档表原 `room_id` 列名暂不批量重命名，明确其语义为固定归档 gameId；新增关联层负责映射，不把这个值当作实时房间 ID。所有旧归档操作从固定 gameId 找到参与者、官方事实和私稿，只有“确实是当前局”时才允许查询运行状态。失去运行状态的旧局只读独立保存的事实、修订与回放；不能从新局补数据。

新增每局回放快照及重开命令收据。自动回放使用当前 `finalReplay` 最终有效操作投影，不重新归档已明确取消的中间输入；手动局保留原官方事实、胜负来源或“仅结束记录”标记，不伪造自动事件或可靠胜负。原公开管理审计与法官审计按固定 gameId 独立保留，旧私密审计继续受原权限限制，不能进入公共回放。归档就绪条件由同一事务完整验证，不以“存在任意草稿”或“有人收藏”代替。

## 归档与重开事务

新命令携带 `requestId` 和 `expectedGameId`，服务器从当前登录会话取得 actor。收据绑定发起者、房间、请求 ID 和完整有效载荷；相同请求返回同一个新局 ID，同 ID 不同载荷拒绝。

一个 SQLite `BEGIN IMMEDIATE` 事务内依次完成：

1. 验证有效会话和原房主身份；临时管理、法官及管理员无自动重开权。
2. 验证该动作收据；重试仍需当前合法权限，不能用收据获得旧身份或秘密正文。
3. 验证 `expectedGameId` 为当前局，且自动或手动结束状态已成立；未结束或待结束申请不得重开。
4. 固化原局参与者、角色与板子快照、官方事实、胜负及来源、手动修订和可用回放，验证独立读取所需数据齐全。保存归档无需发布作者草稿或自动添加收藏。
5. 建立唯一下一局与命令收据，清理当前运行状态，更新 head。出现异常全部回滚，提交前不广播、不让客户端提前返回候场。
6. 提交后广播新公开快照；丢失广播或响应时，重连读取 head 和收据恢复，无需再次发起不同动作。

两个不同请求同时针对同一旧局时，只能一个成功；另一个得到局已切换并读取当前状态，不能再创建第三局。重启后仍按持久收据返回同一个结果。新局未结束前不能再次重开。

## 新局保留与重置

保留房间和房间号、成员 ID/会话/昵称/座位、原房主、测试房间隔离标记、板子配置及发牌/法官模式。候场继续使用现有板子人数与玩法校验，缩减人数前仍需超出范围玩家自行取消入座。

清空全部成员准备状态、身份及确认、夜/日状态、技能与次数、票型和待投输入、阶段计时与历史、暂停/恢复状态、临时管理授权、法官任职和补录草稿、旧语音租约及去重状态。设置版本和房间 revision 递增，拒绝前一局的准备与动作。未来投票默认值按新房间现有默认初始化，不把上一局管理设置带入新局。

归档的个人草稿、发布版本、删除屏障、收藏、分享、评论和通知仍属于原 gameId，均不参与实时状态清理。每个运行表必须在实现前归类为“保留/重置/归档”，用测试核实新加入的表不会遗漏。

## API、授权与客户端

- 新增房间级重开 POST，严格验证输入、来源、房主和请求上下文；返回新局 ID 和公开候场快照。
- 新增显式 `/api/games/:gameId/...` 的记录与归档访问入口。原 `/api/rooms/:id/record*` 兼容入口固定指向原 ID 的首局，不能随 head 跳到第二局。记录 ID 或分享 token 的现有入口保持独立、固定。
- 实时私密读取和局内写入统一携带 `X-Wolf-Game-Id` 请求头，在与业务操作同一事务内验证；重开命令自身还带 `expectedGameId` 字段，二者必须一致。第二局起缺少请求头的旧客户端必须重新载入，不能默认绑定当前局。公共房间读取可返回当前局快照，但不得附带秘密。
- 已有 turnId/settingsRevision/controlVersion 等校验继续保留，gameId 不能替代原防并发机制。所有实时写入与私密入口使用同一门禁，包括身份收集、准备、发牌、开局、夜间、白天、法官、手动管理、语音租约和测试专用接口。
- 旧局授权只看旧局归档参与者和既有分享规则；后来加入第二局的玩家不能因此读取第一局。新局私密信息只按新局会话、成员和法官任期授权；上一局公开的身份不能带到新局公共快照。
- 客户端以 `(roomId, gameId)` 为局内组件和私密请求的生命周期键。收到新局时先清除身份、技能、法官、结束页和临时弹窗，再呈现候场；迟到响应必须同时匹配 session 和 gameId。后台隐藏及前台重同步规则继续保持。
- 原房主在结束页显示“再来一局”，确认文案说明将先保存上一局、保留座位并要求重新准备；只有归档事务提交后才提示已保存。请求中禁重复点击，失败留在原结束页；响应丢失复用同一 requestId 重试。其他玩家看到“房主已开启第 N 局”。我的记录/收藏用房间号加局号区分，版本和删除操作仍绑定具体记录。

## 清理、备份与验收

24 小时实时清理保持原边界。收藏/有效分享等现有保护由 gameId 映射到所属实时房间，不因为后续局 ID 不同失效；删除收藏触发的活动时间也映射回实际房间。任何单局删除不能删除同房其他局或官方事实。

只在合成内存库及临时独立 SQLite 文件验证迁移、重启和故障回滚。现有 BETA-009/010 的生产持久化、备份配置和上线验收仍独立待办，不绑定部署平台；本批不部署、不恢复或覆盖真实库。

实现后必须覆盖：

1. 自动与手动双局、原座位重新准备和私密发牌；第三局持续有效，首局及历史 ID 不变化。
2. 重复 requestId、冲突载荷、两个房主会话并发、旧结束页的不同请求、提交后断网和重新启动。
3. 在归档写入、重置和 head 更新处注入失败，整个事务回滚；旧局事实/私稿/收藏/分享逐项不变。
4. 第一局发布、未发布私稿、收藏、有效分享、纠错、删除与第二局修改彼此隔离；旧参与者与后加入玩家权限不同。
5. 旧请求缺少/携带错误 gameId、重连、迟到身份与法官响应、后台返回和跨账号切换均不越权；所有局内入口都经过门禁。
6. 旧数据库迁移两次、新局重启继续、24 小时实时清理、收藏/分享保护、备份及新文件恢复；历史不依赖新局的实时状态。
7. `npm test`、`npm run typecheck`、`npm run build` 和完整浏览器 E2E；iPhone 实机、多手机、锁屏/弱网另行验收。
