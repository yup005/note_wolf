Sources: [Owner item 26](../../PRODUCT_DECISIONS.md#owner-decisions-2026-10-12), H-004, requirements NOTICE-001–005. ## User outcome

Logged-in users have a header “通知” entry, unread count and mobile center. Include record updates, direct replies, comment likes, moderation and account/VIP changes. Update/reply/like subscriptions default off; account/moderation messages are mandatory. Users can mark one/all read, delete one, clear, and manage the three optional settings. Actual notifications expire 30 days after generation, independently of source records/favorites/comments/audit. No phone push, external messaging, payment or deployment.

Engineering defaults: direct replies notify their immediate parent author, self replies/likes do not notify; no optional self-publication notification. Optional subscriptions apply to subsequent novel events, never replay old actions on toggling. Each reply is separate; one current like notice per recipient/comment aggregates novel subscribed likes, becomes unread on a new like, and retains its original creation/expiry time. After clearing/expiry a genuinely new like may create a new notice; replayed old likes cannot resurrect it. Existing mandatory moderation messages within 30 days migrate once; cleared messages never reappear after restart. No general administrator broadcast composer in this batch; account/status/VIP and existing community messages cover mandatory sources, further management remains separately indexed.

## Privacy and authority

Notification lists contain generic optional-message titles/count/time only, never private notes, comment text, game roles/skills, other account IDs or share tokens. Mandatory reason/status details are visible only to the affected account. Every list/settings/read/delete/clear/open/retry rechecks current active account; ordinary admins cannot read other people's inboxes. Guest receives LOGIN_REQUIRED; revoked sessions cannot replay receipts. Notifications do not enter room snapshots/speech/logs or renew runtime-room activity.

Store exact source authority at event time. A commenter’s original record/share/shared-favorite scope is retained server-side for replies/likes; never give them the replying actor's bearer. Legacy comment source may be recovered from its existing validated creation-request metadata bound to the same author/comment; otherwise only existing participant authorization permits a fallback, never a guessed share. Missing authority stays generic unavailable. Record-update recipients come from currently authorized record favorites and original-link shared favorites, at most one update notice per recipient/version. Revalidate original source both when listing availability and when opening. Withdrawals/deletion, VIP expiry, account disable, regenerated old shares or removed source favorites cannot be bypassed; no fallback to a new token or another author's record. Optional notice text remains generic if unavailable. Source secrets remain server-only until an explicitly authorized own open returns that user's original destination.

Open resolves a destination, not new authority. Viewer components read the source again and clear content/target focus on permission loss. Direct reply/like navigation shows the exact current comment plus immediate parent, even outside current pagination; deleted parents are tombstones and deleted target body stays hidden. An owner-scoped focus read validates scope and room before returning public projections.

## Fixed wire interfaces

New `packages/contracts/notifications.ts`:
- `NotificationSettings {revision:number;updates:boolean;replies:boolean;likes:boolean}`.
- `NotificationItem {id:string;kind:'record-update'|'reply'|'like'|'account'|'moderation';title:string;body:string|null;createdAt:number;updatedAt:number;count:number;revision:number;readAt:number|null;available:boolean}`. `body` is only mandatory account/moderation detail; optional null.
- `NotificationPage {accountId:string;items:NotificationItem[];nextCursor:string|null;unreadCount:number;watermark:number;settings:NotificationSettings}`.
- `NotificationTarget {scope:CommunityScope;focusCommentId?:string}`. Only returned by successful own open.
- GET `/api/notifications` strict query optional `cursor:string`, `limit` 1–50 (default20), -> NotificationPage. Signed owner-bound stable keyset cursor; sort updatedAt/id descending, client dedupes IDs.
- POST `/api/notifications/settings` strict `{requestId:UUID,expectedAccountId?:UUID,revision:nonnegativeInt,updates:boolean,replies:boolean,likes:boolean}` -> `{settings}`. Optimistic revision, exact retry receipt.
- POST `/api/notifications/command` strict `{requestId:UUID,expectedAccountId?:UUID,action:'read'|'delete'|'read-all'|'clear',id?:UUID,version?:positiveInt,through?:nonnegativeInt}` -> `{applied:true}`. Single actions require id/version and prohibit through; bulk require through and prohibit id/version. `version` matches item.revision. Use a monotonic per-account content-change sequence shared by item revisions and that account's watermark, never expose other accounts' event volume. ReadAt-only changes need not create a new content revision. Bulk only affects own rows revision <= list watermark, so concurrently arriving/aggregating notices survive stale bulk commands. Exact same request/body idempotent even after deletion; mismatches invalid. Conflicts `STALE_NOTIFICATION`.
- POST `/api/notifications/:id/open` strict `{}` -> NotificationTarget, current own source validation; no bearer or post body in list. Opening does not itself mutate read state; client uses command after successful authorization.
- POST `/api/community/focus` strict `{scope:CommunityScope,commentId:UUID}` -> `{comment:CommunityComment,parent:CommunityComment|null}` after original-scope validation. Read tombstones, never deleted bodies, no cross-room ID lookup.
- `FavoriteItem.hasUpdate?:boolean` for record/shared favorites only. Separate persisted seen-version per favorite owner/kind/id; initial favorite/legacy migration starts at current version. New publication sets flag independently of notification settings; opening a current valid source clears it. Viewing an older version does not acknowledge newer content. Unavailable favorites do not expose an update marker derived from unauthorized content.

## Storage and integrations

Use a focused NotificationsStore. All source generation and its record/comment/like/moderation/account mutation must share a transaction. Prefer wrapping existing LobbyStore mutations; optional AuthStore callback handles direct account/VIP state writes, only on actual changes. Source-event dedupe is recorded even when subscription is off, so later retry/toggle cannot backfill. Seed existing publication versions/comments/likes as consumed on migration; retrying an old action after upgrade must not create a new optional notice. Keep minimal no-body source/receipt markers separately from expiring notification rows.

Store original comment authority independently before optional generation, including while settings are off. Existing source source logs are not inbox state. Migrate recent community notices once and preserve community audit/restriction histories. Cleanup removes expired notification rows and expired legacy community-notice display rows, never audit, requests, restrictions, records or favorites. Run on startup, reads/writes and existing 60-second maintenance, with cleanup exposed for injected-clock tests. Like merge expires from createdAt, not updatedAt.

Integrate published record events, source comments/likes, moderation, and account status/VIP changes, without duplicate notifications on lost acknowledgements. Account-binding transfers guest favorite seen versions safely alongside existing favorite migration; account inbox/settings never migrate to a different account. Newly created favorite starts seen at current version; cancellation cleans seen metadata so re-adding starts fresh. Notification source validation, community source checks and favorite-library search/listing use raw readers without acknowledging favorite updates; actual browser content GET acknowledges seen state. Guest seen migration preserves unseen update flags and follows the surviving favorite relationship.

UI: lazy header bell/center keyed by account and session revision; generic unread badge, paged list, accessible settings and read/delete controls, clear confirmation, 44px targets at 320/390/430px. Preserve immutable command IDs through network/5xx/408/429 ambiguity; definitive stale conflict rereads without silently resubmitting. Background/account transitions clear private list/targets and ignore delayed responses. Existing AccountDialog may retain current comment restriction, but message history should route to the shared center so a cleared message does not persist in a second inbox. Preserve existing published reader behavior and comment drafts on ordinary version changes. No auto-navigation to secrets or day/night speech.

Review hardening: new UI always includes its rendered expectedAccountId in immutable settings/command intents. Server compares this precondition against the current authenticated account before any receipt or inbox mutation; mismatch is UNAUTHORIZED/401, never an account-selection capability. Optional field preserves older caller compatibility. Retained-intent retries remain disabled until a fresh own-account list validates the center; successful Bell owner mismatch and revoked sessions discard pending intent. Pagination preserves the initial first-page watermark until a genuine full refresh. Authenticated actual raw-share content GET acknowledges only that account’s existing exact-original-token favorite; anonymous reads and raw validators never acknowledge.
