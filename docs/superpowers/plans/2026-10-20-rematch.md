# Same-room Rematch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for native execution, or superpowers:subagent-driven-development if the owner chooses delegated execution. Steps use checkbox syntax for tracking.

**Goal:** 已结束对局由原房主原子归档后开启独立新局，保留房间、会话和座位，保护所有旧记录及跨局秘密。

**Architecture:** 实时状态继续以 roomId 存储，新增 gameId 注册与当前局 head。记录层明确区分固定归档 gameId 和可选的当前运行 roomId；旧记录键、收藏和分享 token 不迁移。重开使用持久命令收据与 SQLite immediate 事务，实时私密读取和写入验证请求绑定的 gameId。

**Tech Stack:** Node.js 24+、TypeScript、better-sqlite3、Express、Socket.IO、React 19、Vite、node:test、Playwright。

**Spec:** [已审阅设计](../specs/2026-10-20-rematch-design.md)。Owner 在设计提交后回复“继续”（2026-10-20）；Owner 再次继续，批准由主代理本会话顺序实施，最终证据见报告。

## Global Constraints

- 房间 ID、四位房间号、玩家会话和座位保持，新一局回到候场，重新准备和发牌。
- 第一次迁移中，现存房间及独立归档的首局 game_id 使用原 ID；迁移事务可重复运行。
- 原 `/api/rooms/:id/record*` 兼容入口固定指向原 ID 的首局，不能随 head 跳到第二局。
- 实时私密读取和局内写入统一携带 `X-Wolf-Game-Id`；第二局起缺少请求头的旧客户端必须重新载入。
- 既有 turnId/settingsRevision/controlVersion、参与者/作者/VIP/法官权限继续成立；管理员无自动重开权。
- 24 小时实时清理保持原边界；历史事实、草稿、发布版本、收藏、分享、删除屏障与审计独立保留。
- 不新增玩法，不实现 PWA、大屏、战绩、教学或其他未授权功能；本计划只落实 REMATCH-001。不部署、不访问真实库，BETA-009/010 生产验收独立。
- 代码完成前运行 npm test、typecheck、build 和完整 E2E；实机验收不由 Chromium 模拟替代。
- 工作在当前 work 分支，保留已有变更；按完整交付批次维护文档并正常提交推送，不按每个小步骤推送，不合并 PR。

## Review Focus

- 服务已提交但手机未收到响应：同 requestId 与旧 gameId 重试仍返回原新局，不能被通用 stale 门禁提前拒绝（任务 3、4）。
- 首局归档键恰好等于仍存在的房间 ID：历史纠错、官方更新和删除不得查询第二局实时表（任务 2）。
- 保持相同成员和相同角色的下一局：旧异步私密响应仍必须被 gameId/session 生命周期拒绝（任务 5）。
- 第二局收藏或分享保护实时房间：不能再靠 archiveId 与 roomId 直接相等来决定 24 小时清理（任务 6）。
- 旧法官和语音拥有者继续在线：归档后保留历史审计，但任职、租约、去重和正在播放的音频都失效（任务 3、5）。

## 文件职责与固定接口

新增 `packages/contracts/rematch.ts`（命令、结果、错误）；`packages/storage/roomGames.ts`（注册、当前局、归档定位、收据和 reset 表清单）；`apps/server/gameScope.ts`（路由范围与请求头验证）；`apps/web/src/RematchControl.tsx`（确认/重试）；`apps/web/src/gameApi.ts`（捕获固定上下文的请求客户端）；`apps/web/src/GameRecordPanel.tsx`（历史对局编辑入口）。不把重开事务、历史导航或请求上下文塞进现有大型组件。

共享类型：`GameRef={gameId:string;roomId:string;gameNumber:number}`；`RematchCommand={requestId:string;expectedGameId:string}`；`RematchResult={game:GameRef;view:LobbyView}`；`GameRecordContext={game:GameRef;code:string;board:RoomBoardSnapshot|null;ended:boolean;isOriginalHost:boolean}`。`RematchResult.game` 是命令固定结果，`view` 是当前授权快照，若很晚重试时又已推进第三局，客户端只把当前 view 用于导航，不从旧结果拼接快照。`RoomSnapshot.gameId/gameNumber` 必填；历史 OwnRecordSummary 保留原 roomId（旧归档键）并新增 gameId/gameNumber/originRoomId，其他历史列表采用同一明确语义，不静默改变旧字段。禁止靠推测 ID 区分归档和实时数据。

`RoomGamesStore(db, now)` 提供 `initialize(roomId):GameRef`、`current(roomId):GameRef`、`info(gameId):GameRef`、`runtime(gameId):string|null`、`assertCurrent(roomId,expectedGameId:string|undefined):void`。找不到对象抛既有 NOT_FOUND/ROOM_NOT_FOUND；不匹配或第二局缺头抛 `STALE_GAME`（409）。首局无头兼容；提供错误头即拒绝。所有业务读取先完成会话和对象授权，不能通过 scope 错误返回秘密或未授权局详情。

`api<T>(path,body?,options?:{gameId?:string}):Promise<T>` 只负责传递显式上下文；`gameApi(roomId,gameId)` 返回绑定的 `request<T>(suffix,body?)`，不使用全局“当前局”变量给旧闭包自动换头。归档访问用固定 gameId 路径，不套实时 current 校验。
